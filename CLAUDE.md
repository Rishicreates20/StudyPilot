## Architecture rules (non-negotiable)

- Modular monolith. FastAPI owns business logic, authorization, grading and AI orchestration. Next.js is presentation only; do not duplicate business rules in the frontend.
- Schema source of truth is `supabase/migrations/*.sql`. **No Alembic, no ORM-generated DDL.** One migration per slice, with RLS, explicit grants and database tests in the same change. Never ship a table without RLS (a guard test fails the build). New `public` tables get Supabase's default grants, so every migration revokes them and grants back only what the API needs.
- Data access is psycopg 3 with explicit SQL (ADR-021), in `app/repositories`. Every user request runs inside `Database.user_transaction(principal)`, which assumes the `authenticated` role with the verified claims; repositories take the `UserConnection` it yields and **also** filter on `user_id`. Routers never obtain a connection any other way.
- **Identity comes only from the verified token** (`get_principal`). Never read a user ID from a body, query string, header or form field; request bodies use `extra="forbid"` so a field naming an owner is a 422. Test every new endpoint for: no token, bad token, another user's resource (404).
- Every user-data table has `user_id`; child tables use composite FKs `(parent_id, user_id)`.
- Answer keys and explanations live in `question_answer_keys` and are never returned before submission.
- `Database.system_session()` (privileged: bypasses RLS) exists for the worker only (`app/jobs`, `app/worker.py`). A test (`tests/test_architecture_rules.py`) fails the build if `api`, `services`, `repositories` or `schemas` mention it. Functions that take a `SystemConnection` filter by `user_id` explicitly.
- Non-owned or missing resource → **404**. Errors are RFC 9457 problem+json; never leak stack traces, prompts, tokens or secrets. Never log tokens, emails, passwords or user-authored text.
- The Supabase **service-role / secret key is not used anywhere** and must not be added without a recorded decision. Only the publishable key is public.
- Roadmaps are **immutable versions** (ADR-029): never edit a stored plan; a regeneration or revision adds the next version, and clients can only switch which one is `current`. The worker is the only writer of `roadmaps*`, `generation_jobs` state and `ai_usage_events`. One queued/running job per goal is enforced by a unique index. Never log goal text, revision notes, prompts or model output (identifiers and codes only); job errors shown to learners come from fixed `user_message`s, never from provider text.
- **Lessons (M4, ADR-032…035):** a lesson is a typed document (`app/ai/lesson/schema.py`): the model fills in the loose, flat `DraftLesson`, code builds the strict `Lesson` (discriminated blocks, ids assigned by code) and checks it (`validation.py`, one repair, then `LESSON_INVALID`); nothing in a lesson's text may become HTML or a link, and no citation may name material that was not supplied (none exists before M6). Lessons are versions, written only by the worker (`lessons` has no client write grants); only the learner's own `lesson_progress` is written through the request transaction. A lesson job may only name a topic of the *current* roadmap (database trigger). Keep `DraftLesson` looser than `Lesson` (cosmetic text is trimmed, never a reason for a second model call), and measure the reading position from scroll geometry, not visibility events.
- **Quizzes (M5, ADR-036…038):** `question_answer_keys` has row security on, **no policy and no grant**, and is named only in `app/jobs/quiz_store.py` (writes it) and `app/grading/attempts.py` (reads it at submission); tests fail the build if request code (`api`, `services`, `repositories`, `schemas`) mentions the table or if anything but `services/quizzes.py` imports `app.grading`. `app/grading` is privileged (`system_session`) and is given only the caller's identity and what they submitted: it checks the submission against the quiz's own questions first, grades multiple-choice and true/false by comparing option ids, and **copies the feedback (right answer, explanation, rubric) into the learner's `quiz_answers` row**, so reading results never touches the key table and nothing is revealed before submission. Attempts, answers and `topic_mastery` are written only by the grader and worker. A quiz is submitted once (`unique (quiz_id)`; `QUIZ_ALREADY_SUBMITTED`); a repeat with the same `Idempotency-Key` returns the same attempt; practising again is a *new* quiz, whose focus objectives the server picks from stored mastery (never the client) and which is told the earlier prompts so it does not repeat them. A short answer is marked in a `grade` job against its fixed rubric: the model only says which rubric points are met, **code adds up the points**, the result is labelled "AI estimate", and the learner's own review (`self_review`, points recomputed server-side) always wins over the job. Mastery is `app/learning/mastery.py` (pure; recency × difficulty weighted; `algorithm_version` stored) and the next step is `app/learning/recommend.py` (pure, ordered rules); the band and the "early estimate" flag are derived from today's thresholds at read time, so keep reading them through `band_for` and never trust the stored `band` column for display. A low score means a targeted practice quiz, never a restart of the course. The model-facing `DraftQuiz` is loose and flat like `DraftLesson`; the sample banks of the test provider carry on through each bank, so keep `sample_quiz` repeat-free.
- **Documents (M6, ADR-039…045):** what a file is comes from its **bytes** (`app/documents/sniff.py`), never its name or `Content-Type`; extraction is pure-Python (`pypdf`), bounded, non-rendering. Files live in the **private** Supabase Storage bucket `documents` at `{user_id}/{document_id}/…`, reached with **the learner's own token** (`SupabaseFiles`); the worker reads through a per-object signed link the API puts in the job's `request` (removed when the job ends). `LocalFiles` is for development/tests and is refused in staging/production. **Supabase Storage has never been run for real**: it is tested on a mock transport, and CI's stack excludes `storage-api`, so the migration guards the bucket/policies behind `to_regclass('storage.buckets')`. The `document` job has two tasks (`extract`, `index`), replaces pages and passages atomically, and **always leaves its document in a final state** (runner hooks + reaper). Anything OCR'd that is not `clear` stops in `review` until the learner confirms; pages are editable only then. Retrieval (`app/retrieval`) is exact, hybrid (cosine + `simple` full-text, RRF) and filtered by `user_id` and `goal_id` **in SQL** (the `<=>` operator is schema-qualified `OPERATOR(extensions.<=>)`); **no result is a valid answer**; no HNSW index until measured. Only `jobs/` and `grading/` may use the privileged session, so `app/retrieval` takes a plain `AsyncConnection`. A grounded lesson cites **labels** (`S1`/`P2`) that code resolves to real ids (`app/ai/lesson/grounding.py`); the model is never told a page or an id, `PAGE_CLAIM` rejects page numbers, and `Lesson.grounding` (`sources` / `no_match` / `none`) is set by code. Citations are resolved when a lesson is read; a deleted document leaves no text behind. Uploaded text is data inside the `<learner_data>` fence, never instructions. **The roadmap planner reads documents too (ADR-047):** the worker passes the goal's `ready` documents as a labelled contents list (`app/ai/roadmap/material.py`; `S1`/`C3`, section headings and pages, no passage text), `ground_evidence` swaps the labels for real ids before storing, and `PAGE_UNKNOWN` rejects a page the material does not have. **A spent daily allowance is `AI_QUOTA_EXHAUSTED`, not "busy" (ADR-046):** it is never retried; `GEMINI_FALLBACK_MODELS` and `GEMINI_THINKING_LEVEL` exist because the free tier allows about 20 generation requests per model per day, so expect quota errors during long sessions.
- **Flashcards (M7, ADR-050):** the browser sends only a rating and a per-showing `Idempotency-Key`; the server locks the card, computes the next schedule with `app/learning/scheduling.py` (pure, `sm2-v1`) and appends a review recording the schedule before and after and the scheduler version. Learners cannot set a schedule when creating a card or edit history (column grants). Changing the rule means a new scheduler version, never a rewrite of history.
- **Exports (M8, ADR-049):** the API never renders; it validates the request, makes a one-object signed upload link **with the learner's token** (stored in `exports.upload_token`, hidden by column grants) and queues an `export` job. Renderers in `app/exports` are pure (an architecture test forbids database, storage, job and network imports; only `files.py` talks to storage); the worker reads the source through the same repository functions the API uses, so an export shows what the learner sees. One export per source, format and `TEMPLATE_VERSION`: changing a layout means a new template version. A character no bundled font covers is replaced visibly and **counted**, never silently dropped. Download file names are ASCII slugs made by code; the web download route redirects only to this project's own `exports` bucket. `uharfbuzz`, the Pillow and lxml that `fpdf2` and `python-pptx` pull in, and `pypdfium2` (tests only) are native code: re-test them when Smart App Control changes its mind.
- Prompts are versioned (`roadmap-planner/v2`, `lesson-writer/v2`, `quiz-writer/v1`, `short-answer-grader/v1`): changing the wording means a new version string, not an in-place edit once roadmaps exist. Learner text goes inside the escaped `<learner_data>` fence. `LLM_PROVIDER=fake` is for local runs and tests; its plans say they are samples and the API refuses it in staging/production.
- All AI calls go through `LLMProvider`. Structured outputs are always re-validated with Pydantic. Plan feasibility, citations and answer keys are validated **by code**, not by asking the model. Models have no tools. Uploaded content is data, never instructions.
- One job queue: PostgreSQL (`SKIP LOCKED`, leases). No Redis. Jobs checkpoint per stage and are idempotent.
- Never fabricate AI-generated learning content, video URLs, timestamps or citation IDs to make the product look complete. `FakeProvider` is for tests only and is refused in staging/production.
- API contract = FastAPI OpenAPI. After changing a route or schema run `npm run contracts:generate` and commit `packages/contracts`; CI fails on drift.

### Web conventions (Next.js 16 — verify against `node_modules/next/dist/docs/` before using an API)

- **Cache Components is on.** Request-time work (fetching live data, `Date.now()`, `Math.random()`, request headers, cookies) must sit under a `<Suspense>` boundary and, when it is inherently per-request, start with `await connection()` from `next/server`. Route handlers that report live state must do the same (see `app/api/health/route.ts`). Never call `new Date()` / `Date.now()` in a Server Component outside that.
- The error boundary prop is `retry` (not `reset`/`unstable_retry`). `LayoutProps<"/">` / `PageProps` types come from `next typegen` (run by `npm run typecheck:web`). The request interceptor is `src/proxy.ts` (not `middleware.ts`).
- **Auth:** sessions are server-side only. Never add `createBrowserClient` or store a token in `localStorage`/`sessionStorage`: the session cookies are written `HttpOnly` by `src/lib/supabase/cookies.ts` and the browser client could not read them. Decide who someone is with `getClaims()` (verifies the signature), never `getSession()`. The proxy is UX only; every protected page re-checks the session and the API verifies the token. The email-confirmation route `/auth/confirm` accepts both link kinds (`token_hash` and the built-in template's `code`, ADR-031); a code is validated with `isAuthCode` before it goes anywhere, and `/?code=` is forwarded by the proxy.
- **Redirects:** run every `next`/return-to value through `safeRedirectPath`. When the API rejects a session Supabase still holds, redirect with `sessionEndedUrlFor` (the sign-in page shows its form for that marker); a plain `signInUrlFor` there would loop.
- **No data-dependent redirects on prefetchable pages (ADR-026).** Next's client router caches a redirect seen during `<Link>` prefetch and replays it later, overriding a Server Action's redirect. Pages like the dashboard and onboarding show a prompt instead; only mutations redirect. Anything that builds the Supabase client runs `await connection()` first (`lib/supabase/server.ts` does).
- **Goals:** the lifecycle (legal status moves, archived = read-only, delete only when archived) is enforced by the API *and* the database (ADR-025); change both together and keep `tests/db/test_db_goal_lifecycle.py` and `tests/api/test_api_goal_management.py` in step. Notices after a mutation use `?notice=` through the lookup table in `lib/goals/notices.ts`, never free text from the URL.
- **Live job progress:** the goal page's status card re-renders the page from the server with `router.refresh()` every 2 s while a job is active (no token or polling endpoint in the browser). Page-level redirects remain forbidden on prefetchable pages: the roadmap page shows an empty state instead of redirecting when there is no roadmap.
- **Quizzes:** the quiz page is a native form whose Server Action (`lib/quizzes/actions.ts`) re-reads the quiz from the API and builds the answers from *its* questions (`lib/quizzes/answers.ts`), so a form cannot add a question or an option; a quiz that was already submitted shows a link to its results instead of redirecting (ADR-026), and a double submit follows the 409 to the first attempt's results. The results page re-renders every 2 s while short answers are being marked (`JobProgress`). Band, score and estimate wording come from `lib/quizzes/labels.ts`; correctness is always shown in words and icons, never colour alone. Server Action files may only export async functions: put helpers in a separate module.
- **Forms:** native forms → Server Actions → Zod → API; map the API's field errors back onto inputs; never echo a password in returned state; use one generic message for failed sign-in (no account enumeration).
- Environment access goes through `src/lib/env.ts` (Zod, fail-fast); read `NEXT_PUBLIC_*` only via literal `process.env.NAME` there.
- Use design tokens and the components in `src/components` (see `docs/DESIGN_SYSTEM.md`); never hard-code colours. Server-only tests need `// @vitest-environment node`.
- Zod: use `z.url({ protocol: /^https?$/ })`, not `z.httpUrl()` (it rejects `localhost` and `http://api:8000`).
- `npx shadcn init/add` puts the `shadcn` package under `dependencies`; keep it in `devDependencies` (it is only used for `@import "shadcn/tailwind.css"` at build time) or `npm audit --omit=dev` fails in CI.
- GitHub Actions: pin exact existing tags and check them with `GET /repos/<owner>/<repo>/git/ref/tags/<tag>`; some actions (for example `astral-sh/setup-uv`) publish no floating major tag like `v10`.
- CI's API job runs its tests against a PostgreSQL service container, and the documents migration needs **pgvector**: the service image is `pgvector/pgvector:0.8.0-pg16` (an exact tag, checked on Docker Hub); stock `postgres:16` fails with `extension "vector" is not available`. A genuine-stack test that expects a write to be refused must use a move the guard really refuses (a ready document set to `ready` again is no change, so it is allowed).

## Dev-environment gotchas (primary machine: Windows 11 Home)

- **Smart App Control is on and its verdicts change.** Unsigned native code can be blocked, including things that ran the day before (2026-10-10: the venv launcher and `ruff.exe`). Test any new native dependency early. Never suggest disabling the setting.
- Long paths are disabled: work from a short path, not from deeply nested app-data folders. The current checkout lives under OneDrive, which makes installs slow (a first `npm install` took ~5 minutes); prefer a folder outside cloud sync.
- Write multi-line files and any script containing template strings or backticks with the Write tool, not shell `-e`/heredocs: quoting mangled backticks here more than once. Small heredocs without backticks are fine.
- **Never let a test run reuse the owner's dev servers.** The owner's `next dev` (:3000) and `uvicorn --reload` (:8000, hosted Supabase in its `.env`) may be running; Playwright's `reuseExistingServer` would adopt them and create accounts on the hosted project. Run browser tests on other ports (`E2E_WEB_URL` / `E2E_API_URL`, e.g. 3010 / 8010) and check what listens on 3000/8000 first. Uploads in tests use `DOCUMENT_STORAGE=local` (set in `playwright.config.ts`; the folder `services/api/.data/` is git-ignored).
- Playwright starts the API, the **worker** (`wait: { stdout: /worker\.started/ }`) and the web app, with `LLM_PROVIDER=fake`; no AI key is needed for the browser tests.
- No Docker/WSL here. The API's database tests *do* run locally (real PostgreSQL 16 via `pgserver`), but genuine-Supabase tests run only in CI, and so does the Playwright journey against a genuine stack (it can be run locally only against a stand-in auth server that is not in the repository: say so if you do). Do not claim they passed unless output was observed.
- In Playwright, Next 16 keeps previous routes in the DOM (hidden): query with `getByRole`, which ignores hidden elements, rather than `getByLabel` / `getByText`.
- Git: the default branch is `main`; line endings are LF via `.gitattributes`.

## Security and secrets

- The repository is **public**. Never commit `.env*` (only `.env.example` with placeholders), keys, tokens or connection strings, and never echo them into logs or chat.
- DB URLs, JWT secrets and LLM keys are server-only. Only `NEXT_PUBLIC_*` values reach the browser, and the production bundle must be checked for leaks when auth or env handling changes (see the bundle search in `docs/IMPLEMENTATION_PLAN.md` M1d).

## Definition of done

A feature is done only when: the workflow works end to end · data persists · permissions are enforced · inputs/outputs are validated · loading, empty and error states exist · tests are written **and run with output observed** · nothing regressed · docs match the implementation.

## Process

- Plan → one vertical slice → run checks → inspect the diff → fix → commit. Conventional Commits; short-lived branches; PRs so CI runs.
- Record assumptions in the PRD and technical decisions in the ARCHITECTURE decision log instead of asking routine questions. Ask only when a missing credential, irreversible action or material product decision blocks progress.
- Never claim an external account is configured, a deployment succeeded or a test passed unless a tool confirmed it.
